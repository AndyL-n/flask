# 云平台设备接入与硬件采集需求说明

版本：2026-10-15。适用项目：JDF 环境治理平台，烟厂地块喷淋控制器。本文以现有腾讯云 IoT Explorer 接口为基础；“建议”“目标”属于本项目接入要求，不代表已经实现。

## 1. 接入范围与现状

| 云设备 DeviceName | 别名 | 关联杆子 | 当前模拟角度 |
|---|---|---|---|
| 3193532260402424 | 一拖二旋转和耙式复合喷淋 | A1-1、A1-2 | 水平270°，俯仰32° |
| 3193232251100970 | 一拖六耙式喷淋 | B1-1～B1-6 | 水平0°，俯仰30° |

本期按两台控制器建立两个云设备，不把八个杆子重复注册为八台控制器。场地围栏、杆子坐标、别名和场地关联由业务数据库维护。DeviceName 是云设备标识，不能直接当作 PLC IP、Modbus 站号或寄存器地址。

现有实现依据：

- `tencent.py` 通过 IoT Explorer 的 `DescribeDevice` 查询连接状态，通过 `DescribeDeviceData` 查询最新属性；控制实际调用的是 Explorer 的 `ControlDeviceData`，`Method=desired`。代码虽创建 IoT Video 客户端，但此控制函数没有使用它。
- `views/device.py` 支持云控制11个属性，等待云属性回读确认，最长30秒。
- 大屏约每5秒刷新数据，场地云同步间隔约10秒；`scheduler_worker.py` 独立运行时每5分钟采集并写入历史。
- 云同步按 `device_name` 查找，所有设备目前共用一个 `TENCENT_PRODUCT_ID`。如两台设备实际属于不同产品，必须先增加设备到 ProductID 的映射，不能继续共用一个产品ID。
- 当前数据库的设备状态和历史记录应由同一次有效采样更新；采集失败不能填零冒充实测数据。

## 2. 总体链路

```mermaid
flowchart LR
    S[PM传感器/水位/接触器/角度反馈] --> P[PLC或控制器]
    P <-->|厂家确认的采集协议和点表| G[MQTT固件或边缘网关]
    G <-->|物模型Topic| C[腾讯云IoT Explorer]
    C <-->|云API读属性/下发控制| B[Flask后台]
    B --> D[MySQL当前快照及运行历史]
    D --> W[大屏地图/设备详情/日志]
```

PLC没有MQTT能力时由网关采集并上云；PLC或控制器已有可用腾讯云MQTT固件时可直接接入。Flask沿用云API同步即可，不必新增一套自建Broker。若改为云端消息推送，应按所用实例配置消息转发/消费服务，不让后台复用设备身份争抢同一个MQTT ClientID。

## 3. 云平台需要交付的配置

| 配置 | 必须提供的值 |
|---|---|
| 平台及地域 | 腾讯云IoT Explorer，实际实例和设备所属地域 |
| ProductID | 每台设备实际所属产品ID；不是16位DeviceName |
| DeviceName | 本文两个设备标识，必须与控制台和数据库完全一致 |
| 物模型 | 本文属性标识符、类型、范围、读写权限；导出JSON作为联调依据 |
| Broker地址和端口 | 从实际实例/设备连接参数取得 |
| 设备认证 | 每设备独立密钥或设备证书/私钥，与所选产品认证方式匹配 |
| MQTT连接参数 | ClientID、Username、Password或证书参数，按设备端SDK/控制台生成 |
| 服务器API凭证 | `TENCENT_SECRET_ID`、`TENCENT_SECRET_KEY`，有对应产品查询和控制权限 |
| 后台产品配置 | 单产品设置`TENCENT_PRODUCT_ID`；多产品需代码支持映射 |
| 设备时钟 | NTP或可靠授时，Unix毫秒时间戳；展示统一北京时间 |

广州域设备常见Broker为 `{ProductID}.iotcloud.tencentdevices.com`；官方文档给出的证书认证端口为8883、密钥认证端口为1883，最终以实际地域、产品认证方式和控制台参数为准。不要仅改端口而省略对应认证流程。见[设备基于TCP的MQTT接入](https://cloud.tencent.com/document/product/1081/102803)、[设备证书认证](https://cloud.tencent.com/document/product/1081/138028)。

本项目建议：MQTT 3.1.1，QoS 1，KeepAlive 60秒，自动重连。认证参数使用设备端SDK生成；云API账号密钥留在服务器，不能代替设备密钥放入PLC或网关。

## 4. MQTT Topic清单

`P` 表示控制台真实ProductID，`D`表示当前DeviceName。上下行以设备视角命名。

| 用途 | Topic | 设备操作 | 方法 |
|---|---|---|---|
| 属性采集上报 | `$thing/up/property/P/D` | 发布 | `report` |
| 属性控制回应 | `$thing/up/property/P/D` | 发布 | `control_reply` |
| 属性控制、上报结果、状态查询结果 | `$thing/down/property/P/D` | 订阅 | 按`method`区分`control`、`report_reply`、`get_status_reply` |
| 告警/故障事件，扩展项 | `$thing/up/event/P/D` | 发布 | `event_post` |
| 事件上报结果，扩展项 | `$thing/down/event/P/D` | 订阅 | `event_reply` |
| 行为执行结果，扩展项 | `$thing/up/action/P/D` | 发布 | `action_reply` |
| 行为调用，扩展项 | `$thing/down/action/P/D` | 订阅 | `action` |

物模型Topic由平台定义，不需要像自定义Topic一样创建Topic类。事件和行为须先在物模型中定义才能使用；本期现有代码主要使用属性控制。见[物模型通信](https://cloud.tencent.com/document/product/1081/138037)、[物模型协议](https://cloud.tencent.com/document/product/1081/34916)。

第一台设备的必配Topic：

```text
发布：$thing/up/property/{ProductID}/3193532260402424
订阅：$thing/down/property/{ProductID}/3193532260402424
```

第二台设备的必配Topic：

```text
发布：$thing/up/property/{ProductID}/3193232251100970
订阅：$thing/down/property/{ProductID}/3193232251100970
```

`{ProductID}`必须替换为实际产品ID。若两台设备属于不同产品，分别替换。设备仅发布和订阅自己的Topic。

## 5. 硬件通信地址交付要求

仓库内 `.smart` 是二进制工程文件，目前没有经过厂家确认的符号点表。本文不将猜测的 M/V/DB 地址或40001等寄存器编号作为实际地址。以下内容必须由PLC程序维护方或厂家填写并逐点联调。

| 类别 | 必须确认的信息 |
|---|---|
| 控制器 | 型号、固件版本、PLC工程版本、网关型号 |
| 以太网采集 | PLC/网关IP、子网、端口、实际协议；S7通信需具体连接参数，Modbus TCP需Unit ID |
| 串口采集 | RS485接线、串口编号、波特率、数据位、停止位、校验、传感器/PLC站号 |
| Modbus点位 | 线圈/离散输入/输入寄存器/保持寄存器类别、功能码、起始地址、地址从0还是1计数 |
| PLC变量点位 | 实际符号名、数据区、字节地址、位号、数据类型；如S7，区分I/Q/M/V/DB实际支持情况 |
| 数值转换 | 有符号/无符号、16/32位、字节序/字序、缩放系数、偏移、单位、无效值 |
| 控制写入 | 单位/范围、保持位还是脉冲、脉冲宽度、请求和反馈是否分开、联锁条件 |

生产点位表每行至少包含：`设备名、云属性ID、硬件变量名、IP/串口、站号、协议、功能码/数据区、地址、位号、长度、类型、字节序、比例、单位、读写方向、采样周期、有效范围、异常处理、厂家确认人`。同一个物模型属性在两台PLC上的地址可以不同。

下面“硬件来源”是信号定义，“实际地址”均需厂家填写。R表示只读采集，RW表示云端设置且必须采集执行反馈。

| 云属性ID | 类型/范围 | 方向 | 硬件来源或语义 | 实际地址 |
|---|---|---|---|---|

| `pm10` | 整数；现有范围0～1000 | R | PM10传感器实测值，厂家确认单位和倍率 | 待确认 |
| `manual_start` | 布尔0/1 | RW | 手动运行请求及控制器接受后的反馈 | 读/写地址分别确认 |
| `cycle_mode` | 布尔0/1 | RW | 循环模式启用状态 | 读/写地址分别确认 |
| `timer_mode` | 布尔0/1 | RW | 定时模式启用状态 | 读/写地址分别确认 |
| `linkage_mode` | 布尔0/1 | RW | 联动模式启用状态 | 读/写地址分别确认 |
| `pm_mode` | 布尔0/1 | RW | PM自动控制模式启用状态 | 读/写地址分别确认 |
| `cycle_run_minute` | 整数0～59 | RW | 循环运行时长的分钟部分 | 待确认 |
| `cycle_run_second` | 整数0～59 | RW | 循环运行时长的秒部分 | 待确认 |
| `cycle_stop_minute` | 整数0～59 | RW | 循环停止时长的分钟部分 | 待确认 |
| `cycle_stop_second` | 整数0～59 | RW | 循环停止时长的秒部分 | 待确认 |
| `oil_change_time_setting` | 整数0～999999，分钟 | RW | 换油提醒设置值；不是实际运行累计时间 | 待确认 |
| `cycle_status` | 布尔0/1 | R | 当前处于循环运行段还是停止段 | 待确认 |
| `pump_status` | 布尔0/1 | R | 水泵实际运行反馈，优先接触器/变频器反馈 | 待确认 |
| `water_in_status_30` | 布尔0/1 | R | 水位达到30%的传感器/PLC判断 | 待确认 |
| `water_in_status_60` | 布尔0/1 | R | 水位达到60%的传感器/PLC判断 | 待确认 |
| `water_in_status_100` | 布尔0/1 | R | 水位达到100%的传感器/PLC判断 | 待确认 |
| `pitch_angle` | 整数-90～90，度 | R | 实测俯仰角；没有传感器时注明为配置角度 | 待确认 |
| `horizontal_angle` | 整数0～359，度 | R | 实测水平角；需转换到地图北0°、顺时针为正 | 待确认 |

PM字段的数据库注释写有mg/m³，但目前页面未说明单位。实施前必须确定传感器实际单位，尤其不能把µg/m³和mg/m³直接混用；统一单位后同时修正文档、物模型、接口说明和页面。传感器若输出小数，需约定缩放整数或调整物模型及存储精度。

`status`、`timestamp`、`off_timestamp`不是PLC寄存器的简单直传字段，应由云连接信息与有效采样派生。`id`、`alias`、`site_id`、`site_name`、`delete`、场地围栏和杆子GPS也不需要当作PLC实时采集点。

水位显示按100%、60%、30%依次判断。若厂家信号为累计阈值，100%时三个值均为1；若信号为独立档位，网关应先统一转换并明确规则。正式接入时读取真实水位，不能持续使用演示中的固定100%。

角度支持范围不等于实际机械限位：旋转设备的软件演示范围20～45°、朝内250～290°仅作为本场地初始配置，真实机械限位和角度零位由厂家提供。耙式设备没有角度反馈时，固定安装朝向是配置值，不能宣称为实测值。

同一设备下多个杆子目前共用设备角度。若A1两个杆子实际有独立旋转/俯仰机构，现有模型不足，需要按喷头编号增加独立反馈和控制映射；云模型、后台接口、地图均需配套调整。

## 7. 建议增加的诊断及自动控制属性

这些字段目前没有完整的后台存储/控制支持，实施时单独评估，不要当成已可调用的字段。

| 属性 | 类型/方向 | 用途与地址要求 |
|---|---|---|
| `fault_active` | 布尔，R | PLC综合故障位，用于派生异常状态；实际地址待确认 |
| `fault_code` | 整数，R | 故障编码及编码字典；故障字/寄存器待确认 |
| `emergency_stop` | 布尔，R | 急停反馈；硬接线保护继续在设备端执行 |
| `local_remote_mode` | 枚举，R | 就地/远程控制许可，决定是否接受远程写入 |
| `sensor_valid` | 布尔或位掩码，R | PM、水位、角度等采样有效性 |
| `plc_comm_ok` | 布尔，R | 网关与PLC通信状态，区别于网关MQTT在线 |
| `pm25_start_threshold`、`pm10_start_threshold` | 整数，RW | PM自动喷淋启动阈值，读写地址待确认 |
| 停止阈值、持续时间、最小启停间隔 | 约定类型，RW | 防抖和滞回；PLC配置地址待确认 |

建议控制逻辑：开启`pm_mode`后，PM有效且任一启动阈值持续超限才启动；低于停止阈值且满足持续时间后停止。启停阈值、持续时间及模式优先级由业务方与厂家签字确认。此前模拟阈值PM2.5=65、PM10=110仅用于演示，不能据此认定生产控制阈值或合规标准。

## 8. 属性上报与控制消息

上线、重连或控制执行后上报全量反馈；正常运行建议每30秒上报一次，状态变化立即上报。设备端内部采样建议1～2秒，告警信号优先采集。频率属于本项目建议，须满足实际实例配额。

现有字段的在线待机消息示例，发布到本设备属性上行Topic：

```json
{
  "method": "report",
  "clientToken": "3193532260402424-report-000001",
  "params": {
    "manual_start": 0,
    "cycle_mode": 0,
    "timer_mode": 0,
    "linkage_mode": 0,
    "pm_mode": 1,
    "cycle_run_minute": 0,
    "cycle_run_second": 0,
    "cycle_stop_minute": 0,
    "cycle_stop_second": 0,
    "oil_change_time_setting": 0,
    "cycle_status": 0,
    "pump_status": 0,
    "pm2_5": 30,
    "pm10": 49,
    "water_in_status_30": 1,
    "water_in_status_60": 1,
    "water_in_status_100": 1,
    "pitch_angle": 32,
    "horizontal_angle": 270
  }
}
```

示例不填写时间，平台使用接收时刻。需要显式采样时间时，增加`timestamp`并填写当前Unix毫秒值，不使用秒值、北京时间字符串或固定示例值。官方物模型文档规定，与服务端时钟相差超过24小时的时间会被拒绝；近30天历史不能直接按原时间用实时物模型report重新上报，应走项目批准的历史导入/补传渠道。[物模型通信](https://cloud.tencent.com/document/product/1081/138037)

云控制属性下行示例：

```json
{
  "method": "control",
  "clientToken": "control-000001",
  "params": {"manual_start": 1}
}
```

设备对同一`clientToken`回应：

```json
{
  "method": "control_reply",
  "clientToken": "control-000001",
  "code": 0,
  "status": ""
}
```

回应随后还必须读取PLC实际反馈并发送`report`，不能仅把命令值回填成运行反馈。后台应区分“云端送达”“控制器接受”“执行反馈确认”三个阶段。[物模型协议](https://cloud.tencent.com/document/product/1081/34916)

同一命令重复收到时按`clientToken`去重，启动/停止采用明确的0或1，不能使用每收到一次就翻转的toggle语义。就地模式、急停或其他联锁不允许启动时，应返回失败原因；数据库保持真实反馈值。

## 9. 后台同步与历史一致性要求

建议按以下规则统一计算业务状态：

| 条件，按优先级 | 业务状态 |
|---|---|
| 云连接离线 | 0：离线 |
| 云在线，但PLC明确故障 | 3：异常 |
| 云在线，无故障且水泵实际反馈运行 | 2：喷淋 |
| 云在线，无故障且水泵停止 | 1：在线待机 |

云在线但PLC采集通信失败，要区分“网关在线”和“硬件数据有效”；应展示采集异常/数据过期，不把旧值当新采样。

现有`tencent.py`先读取云连接状态，再用所有同名物模型属性覆盖结果。如果物模型也定义`status`，可能覆盖连接状态。实施时需单独保留云连接信息，统一派生0/1/2/3；接入`fault_active`后补充异常优先级。不要让设备自行上报一个“在线”位就替代云连接状态。

必须修改/确认的后台行为：

1. 属性ID与本项目字段一一对应；字符串数值、布尔值统一解析后再派生状态，尤其不能让`"1"`与整数1判断不一致。
2. 当前快照与状态变化日志在同一数据库事务中写入，同一个状态、PM、水位、角度和采样时间。
3. 使用可核验的源采样时间或云属性更新时间；拉取相同旧快照不得刷新“最近采样时间”。乱序旧数据不能覆盖新快照。
4. 当前`off_timestamp`在在线或喷淋时更新，语义更接近最后在线时刻；上线前确定接口显示语义，不能把它直接解释为断线时刻。
5. 云端读取失败时保留最后快照并报告同步失败；状态没有变化时不重复写状态变化日志。
6. 历史保存兼顾变化立即记录与周期快照。五分钟拉取可能遗漏短时启停和告警，事件链路启用后用于补足准确运行日志。
7. 当前`get_status_changes`最多读取5000条原始记录再筛选变化；30秒保存一次会超过30天窗口的5000条限制。若保留每5分钟快照，30天约8640条/台，亦超过5000；须增加合理分页、查询范围或单独按变化取日志，保证近30天记录完整。
8. 设备清单按ProductID+DeviceName定位云端；场地和杆子的静态配置不受云属性覆盖。
9. 启用设备控制前，后台必须校验登录身份、场地权限、可写字段、类型、范围及审计记录。目前前端登录门槛不能替代服务器鉴权。

实时同步可沿用API轮询；目标为设备上报后15秒内更新当前大屏、30秒内确认控制反馈。达到目标需协调设备上报周期、API限额及后台轮询。需要更快且完整的状态变化时，应增加云事件转发/消息消费；此部分尚未实现。

## 11. 验收标准

1. 两台云设备独立上线，身份正确且互不挤占连接；八个杆子绑定正确控制器。
2. Topic及报文通过平台物模型校验，控制台和后台能读取全部必需属性。
3. 每个点位做一次现场变化验证；PM、实际泵状态、水位、角度与PLC一致，不以命令值代替反馈。
4. 当前状态、最新历史和大屏一致；在线待机为1，泵运行为2，明确故障为3，云离线为0。
5. PM超限且模式允许时实际启动；解除条件满足后实际停止；阈值、单位和防抖有确认记录。
6. 手动、循环、定时、联动和PM模式的请求、执行、拒绝及恢复均有验证；所有11个现有可控属性逐项测试。
7. 重复控制不反复翻转，乱序数据不覆盖新数据，读写失败不伪造成功。
8. 水位100%展示来自真实传感器；角度指向场地内且符合厂家机械限制。
9. 断网、网关重启、PLC断联、传感器异常均能识别，恢复后重新采样，旧控制请求不盲目执行。
10. 调度进程实际运行且历史连续；近30天日志完整；实时设备与演示模拟数据有明确区分。
